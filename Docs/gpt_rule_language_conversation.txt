===== assistant =====
응. 지금 구조는 이미 **“AI가 조합할 수 있는 문법의 골격”**은 꽤 잘 잡혀 있어. 이제 필요한 건 단순히 개수를 늘리는 게 아니라, **서로 다른 플레이 스타일과 기묘한 상호작용이 나올 수 있도록 어휘를 넓히는 것**이라고 봐.

특히 나는 `Event → Action → Relation → Entity/Form/Element → Temporal/Condition`이라는 현재 구조는 유지하면서, **AI가 예상 밖 조합을 만들 수 있는 Relation / Form / Condition 쪽을 많이 늘리는 방향**으로 가는 게 좋다고 봐. 단순히 `Damage`, `Projectile` 같은 Action만 50개 있어봤자 결과가 “다른 모양의 공격”에 머물 가능성이 높거든.

아래 정도를 **1차 확장 풀**로 제안할게.

---

# 1. Event — 언제 발동하는가

현재 Event는 공격/대시 쪽은 괜찮은데, **이동·상태·공간·소환물과의 상호작용**이 부족해.

| Event | 의미 | 주요 Tag |
|---|---|---|
| `Attack` | 기본 공격 시작 | ATTACK, MELEE, RANGED |
| `Hit` | 적에게 피해를 줌 | ATTACK |
| `Crit` | 치명타 발생 | CRIT |
| `Kill` | 적 처치 | KILL |
| `Dash` | 대시 시작 | DODGE, MOBILITY |
| `DashEnd` | 대시 종료 | DODGE, MOBILITY |
| `PerfectDodge` | 공격 직전 회피 성공 | DODGE |
| `Damaged` | 피해를 받음 | DEFENSE |
| `Guard` | 가드/패링 성공 | GUARD |
| `SkillCast` | 스킬 사용 | SKILL, MAGIC |
| `ComboFinish` | 평타 콤보 마지막 타격 | COMBO |
| `LowHealth` | 체력 30% 이하 진입 | DEFENSE |
| `Interval` | 일정 시간마다 | PASSIVE |
| `CloneSpawn` | 분신 생성 | CLONE |
| `CloneExpire` | 분신 소멸 | CLONE |
| `StatusApplied` | 상태이상 부여 | STATUS |
| **`Move`** | 일정 거리 이동 | MOVEMENT |
| **`Stop`** | 이동하다 정지 | MOVEMENT |
| **`EnterZone`** | 특정 Zone에 진입 | AREA |
| **`ExitZone`** | Zone에서 이탈 | AREA |
| **`ProjectileHit`** | 투사체가 적/벽에 충돌 | PROJECTILE |
| **`ProjectileExpire`** | 투사체 수명 종료 | PROJECTILE |
| **`StatusExpire`** | 상태이상 종료 | STATUS |
| **`StatusStack`** | 상태이상 중첩 | STATUS |
| **`ShieldBreak`** | 보호막 파괴 | SHIELD |
| **`HealReceived`** | 회복을 받음 | HEAL |
| **`SummonSpawn`** | 소환물 등장 | SUMMON |
| **`SummonExpire`** | 소환물 소멸 | SUMMON |
| **`EnemyNear`** | 적이 일정 거리 내 진입 | PROXIMITY |
| **`EnemyFar`** | 적이 일정 거리 밖으로 나감 | PROXIMITY |
| **`FirstHit`** | 해당 적에게 첫 공격 | ATTACK |
| **`NthHit`** | 동일 대상 N번째 타격 | COMBO |
| **`Overkill`** | 남은 체력보다 큰 피해로 처치 | KILL |
| **`NoDamage`** | 일정 시간 피해를 받지 않음 | DEFENSE |
| **`ResourceFull`** | 특정 자원/Charge 최대 | CHARGE |

여기서 특히 `ProjectileExpire`, `StatusExpire`, `CloneExpire`, `ShieldBreak` 같은 **“무언가 끝났을 때” Event**가 중요해.

예를 들어 AI가

> `CloneExpire → Nova → AtTarget → Shadow`

를 만들면 **분신이 죽을 때 그 위치에서 암흑 폭발**이라는 능력이 자연스럽게 나온다.

즉 생성뿐 아니라 **소멸도 사건**으로 만들어주는 거지.

# 2. Action — 무엇을 하는가

여기는 공격만 늘리기보다 **게임 상태를 변화시키는 동사**를 늘리는 게 핵심.

| Action | 의미 | Parameters |
|---|---|---|
| `Damage` | 즉시 피해 | power, radius |
| `Projectile` | 투사체 발사 | count, power, pierce |
| `Nova` | 범위 충격파 | radius, power |
| `Lightning` | 번개 공격 | power, chains |
| `Spawn` | Entity 생성 | duration, count |
| `Heal` | 체력 회복 | power |
| `Shield` | 보호막 생성 | power, duration |
| `Buff` | 능력치 증가 | stat, power, duration |
| `ApplyStatus` | 상태이상 부여 | element, duration |
| `Pull` | 끌어당김 | radius, power |
| `Push` | 밀어냄 | radius, power |
| `Blink` | 순간이동 | distance |
| `ResetCooldown` | 쿨다운 감소 | power |
| `Store` | 값/Charge 저장 | max |
| `Release` | 저장값 방출 | radius |
| **`Drain`** | 피해를 주며 체력/자원 흡수 | power, ratio |
| **`Execute`** | 체력이 낮은 적 추가 피해/처형 | threshold |
| **`Explode`** | Entity/Target을 폭발시킴 | radius, power |
| **`Split`** | 하나를 여러 개로 분열 | count |
| **`Reflect`** | 공격/투사체 반사 | power |
| **`Deflect`** | 투사체 방향 변경 | angle |
| **`Teleport`** | 특정 위치로 이동 | distance |
| **`KnockUp`** | 적 행동을 끊음/띄움 | power, duration |
| **`Slow`** | 이동속도 감소 | power, duration |
| **`Root`** | 이동 봉쇄 | duration |
| **`Stun`** | 행동 봉쇄 | duration |
| **`Taunt`** | 공격 대상 유도 | duration |
| **`Cleanse`** | 상태이상 제거 | count |
| **`Convert`** | 한 자원/효과를 다른 것으로 변환 | ratio |
| **`Extend`** | 지속시간 연장 | duration |
| **`Accelerate`** | 지속 효과의 tick 속도 증가 | power |
| **`Detonate`** | 기존 Status/Entity 즉시 폭발 | power |
| **`Recast`** | 기존 효과를 다시 실행 | count |
| **`Redirect`** | 진행 중 효과의 방향/대상 변경 | — |
| **`CreateZone`** | 지속 영역 생성 | radius, duration |
| **`ModifyProjectile`** | 존재하는 투사체 수정 | speed, size, power |
| **`GainCharge`** | Charge 획득 | amount |
| **`SpendCharge`** | Charge 소비 | amount |
| **`Steal`** | 적의 Buff/상태 일부 획득 | count |

`Detonate`, `Split`, `Convert`, `Extend`, `Redirect` 같은 것들이 상당히 중요해. 이건 **새로운 공격을 생성하는 동사**가 아니라 **이미 존재하는 무언가를 조작하는 동사**라서 조합 폭이 크게 증가한다.

# 3. Relation — 여기 가장 많이 늘리는 걸 추천

현재 시스템에서 **창발성을 가장 크게 담당할 Layer**라고 봐.

Relation을 쉽게 말하면:

> “A가 B와 어떤 관계를 가지는가?”

야.

| Relation | 의미 | 예시 |
|---|---|---|
| `Copy` | 행동 복제 | 분신이 플레이어 공격 복제 |
| `Inherit` | 속성 상속 | 분신이 플레이어 Fire 속성 상속 |
| `Repeat` | 다시 실행 | 0.5초 뒤 공격 반복 |
| `Transfer` | 효과 이전 | 독을 주변 적에게 전달 |
| `Chain` | 다음 대상으로 연결 | 번개 연쇄 |
| `Consume` | 무언가 소비 | Mark를 먹고 피해 증가 |
| `Orbit` | 주변 공전 | Orb가 플레이어 공전 |
| `Mark` | 후속 효과용 표식 | 다음 공격 강화 |
| `SwapPosition` | 위치 교환 | 분신과 위치 교환 |
| `Follow` | 따라다님 | 소환물이 플레이어 추적 |
| **`Mirror`** | 방향을 반전하여 복제 | 오른쪽 공격 → 왼쪽에서도 발생 |
| **`Echo`** | 시간차 복제 | 과거 공격 잔상이 반복 |
| **`Attach`** | 대상에 부착 | Orb가 적에게 붙음 |
| **`Detach`** | 부착 해제 | 붙어있던 폭탄 분리 |
| **`Link`** | 두 Entity 연결 | 두 적 사이 연결 |
| **`Share`** | 값을 공유 | 분신과 피해/버프 공유 |
| **`Redirect`** | 대상을 변경 | 투사체가 다른 적으로 꺾임 |
| **`Return`** | 원래 위치/주인에게 귀환 | 부메랑 |
| **`Bounce`** | 충돌 후 튕김 | 벽 반사 투사체 |
| **`Split`** | 여러 자식 효과로 분리 | 투사체 → 3개 |
| **`Merge`** | 여러 효과를 합침 | Orb 3개 → 거대 Orb |
| **`Replace`** | A 대신 B 발생 | Dash 대신 Blink |
| **`Transform`** | Entity/Form 변화 | Projectile → Zone |
| **`Carry`** | 효과를 들고 이동 | 투사체가 Zone을 운반 |
| **`Anchor`** | 특정 위치/Entity에 고정 | Zone을 Clone에 고정 |
| **`Trace`** | 이동 경로를 따라 효과 생성 | Dash 경로에 불길 |
| **`Seek`** | 대상 추적 | Projectile 유도 |
| **`Avoid`** | 특정 대상/공간 회피 | Orb가 적 탄환 회피 |
| **`Spread`** | 주변 대상으로 전염 | Poison 전파 |
| **`Gather`** | 여러 효과를 한 곳으로 모음 | Projectile 회수 |
| **`Amplify`** | 연결된 효과 강화 | Mark 대상 피해 증가 |
| **`Invert`** | 효과 성질 반전 | Push → Pull |
| **`Synchronize`** | 여러 Entity가 동시에 행동 | Clone 동시 공격 |
| **`Alternate`** | 두 효과를 번갈아 실행 | Fire/Frost 교대 |
| **`Cascade`** | 결과가 다음 효과를 발동 | Kill → Explosion → Kill → Explosion |
| **`BindLifetime`** | A 수명을 B에 연결 | Clone 죽으면 Zone 제거 |
| **`BindPosition`** | 위치 연결 | Zone이 Orb를 따라감 |
| **`BindTarget`** | 같은 대상을 공유 | Clone이 플레이어 타겟 공격 |
| **`ScaleWith`** | 다른 값에 비례 | 이동거리만큼 피해 증가 |
| **`StoreFrom`** | 특정 사건의 값을 저장 | 받은 피해 저장 |
| **`ReleaseTo`** | 저장값을 특정 효과로 방출 | 저장 피해 → Nova |

마지막 `StoreFrom / ReleaseTo / ScaleWith` 같은 관계가 꽤 재밌을 거야.

예를 들어 AI가:

**Damaged → Store → StoreFrom(DamageTaken) → PerfectDodge → Release → Nova**

같은 구조를 만들면

> 맞은 피해가 축적된다.  
> 정확한 회피에 성공하면 축적된 피해를 충격파로 방출한다.

라는 꽤 자연스러운 능력이 만들어짐.

개발자가 **“복수의 충격파”**라는 스킬을 직접 등록한 적이 없어도 말이지.

# 4. Entity — 세상에 존재할 수 있는 것

현재 `Clone / Turret / Orb / Zone / PhantomWeapon` 정도라면 좀 더 늘려도 좋아.

| Entity | 역할 |
|---|---|
| `Clone` | 플레이어 잔상/분신 |
| `Turret` | 고정 공격체 |
| `Orb` | 공전 오브젝트 |
| `Zone` | 지속 영역 |
| `PhantomWeapon` | Grip 없는 무기 잔상 |
| **`Mine`** | 바닥 설치형 폭발체 |
| **`Trap`** | 조건 만족 시 발동 |
| **`Drone`** | 이동 가능한 소환체 |
| **`Wisp`** | 적/플레이어를 추적하는 작은 정령 |
| **`Wall`** | 이동/투사체 차단 |
| **`Totem`** | 주변 효과 제공 |
| **`Beacon`** | 특정 위치를 기준점으로 저장 |
| **`Tether`** | 두 대상을 잇는 연결체 |
| **`Echo`** | 과거 행동의 잔상 |
| **`Shard`** | 수집/발사 가능한 조각 |
| **`Rune`** | 바닥에 설치되는 마법 문자 |
| **`Portal`** | 두 공간 연결 |
| **`Decoy`** | 적의 공격을 유도 |
| **`Spirit`** | 독립적으로 움직이는 소환체 |
| **`Blade`** | 공전/비행 가능한 칼날 |
| **`Seed`** | 일정 조건 뒤 성장/발동 |
| **`Bomb`** | 부착/설치 후 폭발 |
| **`Chain`** | 두 Entity 사이 연결 자체 |

특히 `Beacon`은 별것 아닌 것 같지만 조합 가능성이 엄청 높아.

`DashOrigin → Spawn Beacon`

을 해두면 이후

`SwapPosition Beacon`

`Projectile At Beacon`

`Nova At Beacon`

`Clone Spawn At Beacon`

등의 능력을 AI가 만들 수 있어.

# 9. WorldRule — 이건 오히려 아주 중요하다

현재 WorldRule이 5개뿐인데, AI에게 자유를 주려면 역설적으로 **세계의 물리적 한계는 더 명확해야 해.**

그래야 AI가 자유롭게 생성해도 “말이 되는 범위”를 알 수 있음.

| WorldRule | 내용 |
|---|---|
| `Grip` | 플레이어 2 Grip, Clone 0 Grip |
| `OneSelf` | Self는 플레이어 하나뿐 |
| `Gravity` | 2D 평면 |
| `NoTime` | 시간 역행 불가 |
| `Budget` | 능력 하나당 major mechanic 제한 |
| **`Position`** | 모든 공간 효과는 유효한 world position 필요 |
| **`Ownership`** | 모든 Entity는 owner를 가짐 |
| **`Lifetime`** | 임시 Entity는 생성/소멸 시점 존재 |
| **`Targetable`** | Target 지정 효과는 유효한 Target 필요 |
| **`DeadCannotAct`** | 죽은 Entity는 행동 불가 |
| **`NoDuplicateSelf`** | Clone은 Self 판정을 받을 수 없음 |
| **`Collision`** | Projectile은 충돌 대상을 가져야 함 |
| **`ResourceConservation`** | Consume은 실제 소비할 대상이 있어야 함 |
| **`StoredValue`** | Release는 이전 Store가 있어야 함 |
| **`RelationValidity`** | Relation 양쪽의 타입이 호환되어야 함 |
| **`FiniteLifetime`** | 자기증식 Entity에는 수명/상한 필요 |
| **`FiniteCascade`** | 재귀적 trigger chain에는 종료 조건 필요 |
| **`NoFreeRecursion`** | 자기 자신을 무조건 다시 발동시키는 효과 금지 |
| **`SpawnCap`** | 동시에 존재 가능한 Spawn 수 제한 |
| **`ProcBudget`** | 하나의 Event에서 파생되는 proc 수 제한 |

마지막 4개는 **AI 생성 게임이면 거의 필수**라고 봐.

안 그러면 AI가 우연히

> Hit → Projectile → ProjectileHit → Projectile → ProjectileHit → …

같은 걸 만들었을 때 게임이 폭발한다. 창발적 능력과 무한루프는 종이 한 장 차이다.

# 그래서 전체 Language Pool을 이렇게 생각하면 좋음

네 시스템을 이제 단순히 4 Layer라고 보기보다는 다음처럼 보면 꽤 깔끔해.

| 질문 | Layer | 예 |
|---|---|---|
| **언제?** | Event | PerfectDodge |
| **무엇을?** | Action | Spawn |
| **무엇이/무엇을?** | Entity | Clone |
| **어디에?** | Form | DashOrigin |
| **어떤 성질로?** | Element | Shadow |
| **서로 어떻게 연결?** | Relation | Copy |
| **언제까지/언제 다시?** | Temporal | Delayed |
| **어떤 경우에만?** | Condition | HealthBelow |
| **세계에서 가능한가?** | WorldRule | Grip / SpawnCap |

그리고 이 정도 풀만 있어도 AI가 예를 들어 임의로

**PerfectDodge + Spawn + Clone + DashOrigin + Copy + Delayed + Shadow**

를 골랐다고 해보자.

이를 문법적으로 해석하면:

> 완벽 회피 성공  
> → 대시를 시작했던 위치에  
> → Shadow Clone 생성  
> → Clone은 플레이어가 직전에 수행한 공격을 Copy  
> → 0.4초 뒤 실행

이 된다.

반대로

**Hit + ApplyStatus(Poison) + Stack → Kill + Spread + DeathPoint + NearbyEnemy**

같은 조합이면:

> 공격할수록 독이 누적되고, 독에 걸린 적이 죽으면 남아 있던 독이 죽은 위치를 중심으로 주변 적들에게 퍼진다.

또

**Damaged + StoreFrom(DamageTaken) → PerfectDodge + ReleaseTo(Nova) + AtSelf + ScaleWith(StoredDamage)**

면:

> 받은 피해 일부를 기억한다. 이후 완벽 회피에 성공하면 기억한 피해량에 비례하는 충격파를 방출한다.

이런 식으로 **“복수”, “역병”, “잔상검” 같은 완성된 스킬을 Pool에 넣지 않았는데도 결과적으로 그런 개념이 튀어나오는 상태**가 우리가 원했던 기술언어 방향에 훨씬 가깝다.

그리고 지금 단계에서 내가 가장 추천하는 건 **무작정 Pool을 200개로 키우기보다 `Relation`을 30~50개 정도까지 가장 풍부하게 만드는 것**이야. `Fireball`, `IceSpike`, `ThunderStrike`를 각각 Action으로 만드는 순간 다시 개발자가 기술을 만드는 시스템이 되어버리는데, `Projectile + Element + Split + Seek + Repeat + Transform + Consume`처럼 **적은 primitive를 다양한 Relation으로 엮으면 AI가 기술을 만드는 시스템**이 되니까. memcite

===== user =====
근데 나는 이구조가 좀 단조롭긴 하다고 생각은 되네. 롤토체스의 증강이나, 세피리아의 아티팩트 능력같은거 보면 이 구조로는 도저히 표현할 수 없는 다채로운 능력이 표현되거든? 그래서 뭔가 이 언어의 한계를 뛰어넘어서 새로운 구조를 짜야할것도 같은데 한번 생각해볼래?

일단 방금 말한 롤토체스 증강, 세피리아 아티팩트 능력들을 니가 살펴보고 생각해서 대답해봐

===== assistant =====
응. 실제 사례를 보고 나니까 **지금의 `Event → Action → Relation` 구조를 확장하는 것만으로는 한계가 명확하다**고 생각해.

TFT 증강을 보면 단순 전투 proc뿐 아니라 경제, 상점, 레벨업, 아이템, 증강 선택 자체까지 건드린다. 예를 들어 현재 풀에도 `Augmented Power = 다음 증강의 등급 상승`, `Epic Rolldown = 레벨 8 도달 시 무료 리롤 20회`, `Pandora's Items = 벤치 아이템을 매 라운드 무작위화`, `Golden Egg = 11턴 뒤 큰 보상, 전투 승리 시 부화 가속` 같은 게 있다. Riot도 Augment를 단순 전투 버프가 아니라 게임마다 전략 자체를 달라지게 만드는 장치로 설명한다. citeturn1search2turn1search3

세피리아도 현재 DB 기준 아티팩트가 수백 종이고, 아티팩트 효과뿐 아니라 레벨, 조건, 콤보, 인벤토리 배치와 태블릿 관계까지 빌드의 일부다. citeturn2view0

그래서 나는 **Ability Language를 버리는 게 아니라, 그 위에 한 단계 더 큰 언어를 만드는 것**이 답이라고 봐.

## 1. 지금 언어가 실제로 표현하는 것

현재 구조는 사실상 이거야.

> **Trigger → Effect**

예를 들어

`PerfectDodge → Spawn(Clone) → DashOrigin`

`Crit → ApplyStatus(Burn)`

`Kill → Nova(DeathPoint)`

아무리 Relation이나 Entity를 추가해도 결국

> X가 일어나면 Y한다.

라는 **반응형 전투 효과**다.

그런데 다음 능력을 생각해보자.

> 최대 체력이 절반이 된다. 대신 잃은 체력 1%마다 공격력이 증가한다.

현재 DSL로 억지로 만들 수는 있겠지만 자연스럽지 않다.

더 심각한 건:

> 회복 효과가 더 이상 체력을 회복시키지 않는다. 대신 동일한 양의 보호막을 생성한다.

이건 Action이 아니라 **기존 시스템의 의미를 재정의**한다.

또:

> 이번 층에서 피해를 받지 않고 클리어하면 다음 층의 보상이 2배가 된다.

이건 전투 하나를 넘어 **Run progression**을 건드린다.

그리고 TFT식으로:

> 앞으로 등장하는 세 선택지 중 가장 낮은 등급의 선택지가 제거된다.

이건 아예 **게임의 선택 시스템 자체를 수정**한다.

따라서 언어의 기본 단위를 `Ability = Trigger + Effect`로 두면 안 된다고 봐.

---

# 2. 내가 제안하는 핵심: Ability를 **Rule Graph**로 바꾸자

기존에는:

```text
EVENT
 ↓
ACTION
 ↓
ENTITY
 ↓
RELATION
```

이었다면,

새로운 시스템에서는:

```text
                    ┌── Combat
                    │
                    ├── Player
                    │
                    ├── Enemy
                    │
ABILITY ── modifies ─┼── Skill
                    │
                    ├── Resource
                    │
                    ├── Reward
                    │
                    ├── Choice
                    │
                    ├── World
                    │
                    └── Other Rules
```

즉 능력 하나를 **효과(effect)**가 아니라

> **게임 세계의 규칙을 추가하거나 수정하는 작은 프로그램**

으로 보는 거야.

나는 이걸 임시로 **Rule Language**라고 부를게.

---

# 3. Rule Language의 기본 구조

Ability 하나가 여러 종류의 `Rule`을 가질 수 있게 한다.

| Rule 종류 | 의미 | 예 |
|---|---|---|
| **Effect Rule** | 사건 → 효과 | 치명타 시 번개 |
| **Modifier Rule** | 기존 값을 변경 | 최대 HP -50% |
| **Conversion Rule** | A를 B로 변환 | Heal → Shield |
| **Replacement Rule** | 기존 행동 자체를 대체 | Dash → Blink |
| **Constraint Rule** | 행동을 제한 | 이동 불가 |
| **Scaling Rule** | 상태에 따라 값 변화 | 잃은 HP마다 공격력 |
| **Accumulation Rule** | 장기 상태 축적 | 처치마다 영구 공격력 |
| **Threshold Rule** | 특정 지점에서 변화 | 100 Kill 시 진화 |
| **Spatial Rule** | 위치 관계 | 가까울수록 강해짐 |
| **Meta Rule** | 다른 Rule 수정 | 화염 효과 2회 발동 |
| **System Rule** | 게임 시스템 수정 | 상점 리롤 비용 변경 |
| **Generation Rule** | 미래 선택지 변경 | 이후 Fire 능력 출현율 증가 |

이렇게 되면 기존 `Event → Action`은 없애는 게 아니다.

그냥 **Effect Rule이라는 한 종류**가 되는 거야.

이게 중요한 차이다.

---

# 4. 특히 중요한 건 `Game Object`가 아니라 `Game Concept`을 참조하는 것

지금 Entity는

`Clone / Orb / Turret / Projectile`

같은 **월드에 실제 존재하는 것** 위주야.

나는 이걸 훨씬 넓혀서 `Concept`이라는 Layer로 바꾸는 게 좋다고 생각해.

예:

```text
Combat Concept
```

이게 엄청 중요하다.

# 5. 예를 들어 이런 능력이 가능해진다

### 「피의 계약」

> 최대 체력 40% 감소.  
> 잃은 체력 1%마다 공격력 +1%.  
> 체력이 20% 이하일 때 회복 효과가 보호막으로 전환된다.

이걸 Rule Graph로 보면:

```text
ABILITY: Blood Covenant

Modifier
MaxHealth
× 0.60

Scaling
MissingHealth
    ↓
AttackPower
+1% per 1%

Conversion
IF Health < 20%
Heal → Shield
ratio = 1.0
```

여기에는 **Event가 아예 필요 없는 Rule도 두 개**나 있다.

# 6. 더 중요한 예

### 「마지막 불꽃」

> 화염 상태인 적이 죽으면 주변 적에게 화염이 전염된다.  
> 전염될 때마다 화염 피해가 20% 증가한다.  
> 5번 전염된 화염은 폭발하고 사라진다.

기존 시스템에서는 꽤 복잡해.

새 구조에서는:

```text
Burn
 │
 ├─ on HostDeath
 │      ↓
 │    Transfer → NearbyEnemy
 │
 ├─ on Transfer
 │      ↓
 │    Power × 1.2
 │    Generation += 1
 │
 └─ IF Generation >= 5
        ↓
      Explode
      Remove Burn
```

여기서 중요한 건 **Burn 자체가 상태를 가진 객체**가 되었다는 것.

`Generation`, `Power`, `Host`를 가진다.

그래서 능력이 능력을 수정할 수 있다.

# 7. 그러면 TFT 같은 괴상한 것도 가능해진다

예를 들어 가상의 증강:

### 「도박사의 축복」

> 능력 선택지를 하나 덜 받는다.  
> 대신 남은 선택지의 희귀도가 한 단계 상승한다.

```text
Modify AbilityOffer:

ChoiceCount -= 1
Rarity += 1
```

끝.

전투 Event가 하나도 없다.

---

### 「집착」

> 같은 계열 능력을 3번 연속 선택하면 해당 계열 능력이 이후 더 자주 등장한다.

```text
Observe:
AbilitySelection.Tag

State:
ConsecutiveSameTag

IF ConsecutiveSameTag >= 3:

Modify GenerationRule:
Weight(selectedTag) × 2
```

이건 **AI 생성 시스템 자체와 게임 능력이 상호작용**하는 거야.

이런 데까지 가면 상당히 재밌어진다.

# 8. 세피리아에서 내가 특히 가져오고 싶은 부분

세피리아의 중요한 점은 단순히 효과 종류가 많은 게 아니라, **“내가 무엇을 가지고 있느냐”뿐 아니라 “그것들이 어떤 관계를 맺고 있느냐”가 능력의 일부**라는 점이야. 아티팩트는 레벨·콤보·활성 조건을 가지며, 태블릿은 인접한 아티팩트를 강화하기 때문에 인벤토리 배치 자체가 빌드 시스템이 된다. citeturn0search9turn2search0

우리 게임에서는 굳이 인벤토리 테트리스까지 복제할 필요는 없지만 이 철학은 가져올 수 있어.

즉 **Topology/Relationship 자체를 조건으로 취급**하는 거야.

예:

```text
Count(Fire abilities) >= 3

Count(Dodge abilities) > Count(Attack abilities)

Has(Clone) AND Has(Shadow)

Weapon.Tag == Heavy

Ability A shares Element with Ability B

Skill Q and Skill E have different Elements
```

그러면 이런 능력도 생성 가능하다.

> 가진 화염 능력 하나당 대시 거리가 8% 증가한다.

또는

> 서로 다른 원소를 가진 스킬 하나당 치명타 확률 +5%.

또는

> 모든 능력이 같은 원소라면 해당 원소 효과가 진화한다.

이건 기존 Trigger DSL에서는 매우 표현하기 힘들다.

# 9. 그리고 한 단계 더: **Rule이 Rule을 대상으로 할 수 있어야 한다**

여기가 내가 생각하기에 진짜 핵심이다.

현재는

```text
Player → Enemy
Projectile → Enemy
Clone → Player
```

정도잖아.

새 언어에서는:

```text
Rule → Rule
Ability → Ability
Tag → Ability
Element → Rule
System → Rule
```

도 허용한다.

그러면:

> 모든 `OnKill` 효과가 한 번 더 발동한다.

가능.

```text
SELECT Rules
WHERE Trigger == Kill

Modify:
ExecutionCount += 1
```

---

> 모든 Fire 능력의 조건에서 `Chance`를 제거한다.

가능.

```text
SELECT Ability
WHERE Element == Fire

REMOVE Condition.Chance
```

---

> 대시 관련 능력의 발동 조건을 Perfect Dodge로 변경한다.

가능.

```text
SELECT Rule
WHERE Tag == DASH

REPLACE Trigger(Dash)
WITH Trigger(PerfectDodge)
```

이 순간부터 **능력 하나가 다른 능력의 문법 구조를 바꿀 수 있다.**

이게 TFT/세피리아식 build-defining 효과를 생성하는 데 엄청 강력할 거라고 생각해.

# 10. 따라서 Layer 방식 자체를 버리자

기존:

```text
Layer 2 Relation
Layer 3 Event
Layer 3 Condition
Layer 4 WorldRule
```

보다는

```text
└──────────────┬──────────────┘
               │
          referenced by
               ↓
┌─────────────────────────────┐

│                             │
│ Observe      Modify         │
│ Trigger      Replace        │
│ Convert      Accumulate     │

└──────────────┬──────────────┘
               │
```

# 11. 그러면 AI에게 진짜 자유가 생긴다

예를 들어 플레이어가 현재

```text
Sword
Dash-heavy
Crit 42%
Fire abilities × 2
Clone ability × 1
HP investment low
Perfect Dodge frequent
```

라고 하자.

AI가 이걸 보고 다음 능력을 만든다.

### 「재가 남긴 검」

> 완벽 회피할 때마다 `Memory` 1을 얻는다.  
> Memory가 3이 되면 다음 근접 공격이 분신에게도 복제된다.  
> 복제된 공격은 화염 능력 하나당 20% 강해진다.  
> 발동 후 Memory를 모두 잃는다.

Rule Graph:

```text
PerfectDodge
      │
      ↓
Memory += 1
      │
      ↓
Memory >= 3
      │
      ↓
Modify Next(MeleeAttack)
      │
      ├── Copy → Clone
      │
      └── DamageScale
             ↑
       Count(Fire Ability)
             × 20%

AfterExecution
      ↓
Memory = 0
```

이건 지금 DSL을 억지로 엄청 확장하면 만들 수야 있겠지만, 새 구조에서는 그냥 **작은 프로그램 하나**다.

## 그래서 내가 보는 최종 방향

처음 우리가 만들던 건 사실:

> **AI가 스킬을 조립한다.**

였어.

그런데 TFT 증강과 세피리아를 보고 한 단계 확장하면 목표가 이렇게 바뀌는 게 맞는 것 같다.

> **AI가 게임에 적용될 새로운 규칙을 작성한다.**

그리고 그 규칙 중 일부가 우리가 흔히 말하는 **스킬**이고,

일부는 **패시브**,

일부는 **아티팩트**,

일부는 **증강**,

일부는 **빌드 변형**,

일부는 심지어 **게임 시스템 변형**인 거지.

이렇게 설계하면 굳이 처음부터 `"이것은 스킬이다"`라고 분류할 필요도 없어. AI가 Rule Graph를 생성한 다음 결과를 보고 게임이 `"Active Skill"`, `"Passive"`, `"Augment"`, `"Mutation"` 같은 표현형으로 분류할 수도 있다.

그리고 이 방향의 장점은 **기존에 만든 AbilityLanguage를 버릴 필요가 없다는 것**이야. 지금 만든 `Event/Action/Relation/Entity/Condition`은 새 Rule DSL의 **Combat primitive library**로 그대로 들어간다. 우리가 갈아엎어야 하는 건 단어 풀이 아니라 **그 단어들을 반드시 한 줄짜리 `Trigger → Effect`로 조립해야 한다는 제약**이야.

내 생각에는 다음 단계에서 바로 코딩으로 들어가기보다, **TFT/세피리아에서 구조적으로 서로 다른 능력 20~30개를 골라서 새 Rule Language로 실제 표현해보는 테스트**를 하는 게 좋겠다. 거기서 표현 불가능한 사례가 나올 때마다 문법을 고치면, 이 언어가 어디까지 일반화되어야 하는지 상당히 명확해질 거야. citeturn1search2turn1search6turn0search1 memcite

===== user =====
그런데 생각할 점도, 제약해야할 점도 있어. 첫번째로는 실제로 만들어진 기술을 안정적으로 구현할 수 있어야한다는 것이고, 둘째는 게임의 밸런스에 맞도록 valid 할 수 있어야한단,ㄴ거야. 원래 구조는 단순했기 때문에 어느정도 수치적으로 validate 할 수 있었는데, 이번 구조는 어떤 방식으로 검수할지를 생각해야하고. 또한 실현 가능성에 대해서도 생각해야해

===== assistant =====
맞아. 그리고 이 두 조건을 넣으면 아까 내가 제안한 **“AI가 임의의 Rule Graph를 작성한다”**는 방향은 그대로 쓰면 위험해. 표현력은 엄청나지만, 구현 가능성과 밸런스 검증 가능성을 잃어버릴 수 있어.

핵심 목표를 이렇게 잡는 게 좋겠어.

> **AI에게 무한한 자유를 주는 게 아니라, 검증 가능한 공간 안에서 최대한 자유롭게 규칙을 만들게 한다.**

즉 **표현력(expressiveness) ↔ 검증 가능성(validatability)** 사이에서 설계해야 해.

---

# 1. 사실 검증은 하나가 아니라 4단계여야 함

AI가 생성한 능력 `A`에 대해:

```text
AI Generated Rule Graph
          │
          ▼
① Structural Validation
   "문법적으로 말이 되나?"
          │
          ▼
② Executability Validation
   "게임 엔진이 실제 실행할 수 있나?"
          │
          ▼
③ Safety Validation
   "무한루프/폭발적 연산이 없는가?"
          │
          ▼
④ Balance Validation
   "게임 밸런스 범위 안인가?"
          │
          ▼
      ACCEPT
```

이 네 개를 통과한 것만 게임에 들어가게 하는 거야.

그리고 중요한 점은 **LLM에게 검증을 맡기지 않는다.**

LLM은 생성만 한다.

검증기는 deterministic code여야 함.

---

# 2. 그래서 AI가 C# 코드를 만드는 구조는 절대 피하는 게 좋음

예를 들어 AI가

```csharp
if (player.hp < 0.3f)
{
    foreach (...)
       ...
}
```

같은 걸 생성하게 하면 거의 끝장이야.

안전성도 검증하기 어렵고 성능 예측도 어렵고 버그도 생기고 밸런스 분석도 어려워.

대신 AI는 **선언적인 IR(Intermediate Representation)** 만 생성해야 해.

예를 들어:

```text
Rule {
    Trigger: PerfectDodge

    StateMutation:
        Memory += 1

    Condition:
        Memory >= 3

    Effect:
        Modify(NextAttack)

    Modifier:
        CopyTo(Clone)

    Scaling:
        Count(Ability where Element=Fire)
        * 0.20

    Consume:
        Memory = 0
}
```

게임 엔진에는 이미

`PerfectDodge`, `Counter`, `ModifyNext`, `CopyTo`, `Count`, `Scale`, `Consume`

각각의 **검증된 Runtime Handler**가 존재하는 거지.

그러면 LLM은 코드를 만드는 게 아니라

> 이미 구현되어 있는 안전한 부품을 조립한다.

가 된다.

이건 지금 AbilityLanguage의 철학을 유지하면서 표현력만 훨씬 넓히는 방법이야.

---

# 3. 그러면 “실현 가능한 능력인가?”는 상당 부분 자동 검증 가능

각 primitive에 **타입 시스템**을 붙이자.

예를 들어:

```text
PerfectDodge
Output: EventContext<Player>

Damage
Input: Target<Damageable>

Count
Input: Collection<T>
Output: Integer

CopyTo
Input:
    Rule
    Entity<Actor>

Scale
Input:
    Numeric
    Numeric

Spawn
Input:
    EntityType
    Position
```

그러면 AI가

```text
PerfectDodge
   ↓
Damage
```

라고만 생성하면

```text
ERROR:
Damage requires Target<Damageable>
PerfectDodge does not provide Target.
```

라고 reject.

반대로

```text
Hit
 ↓
Target
 ↓
Damage
```

는 valid.

이게 **Structural Validation + Executability Validation**을 거의 동시에 해결한다.

---

# 4. 더 강력하게 Capability 개념을 넣을 수 있음

Entity마다 가능한 행동을 선언해.

예를 들어:

| Entity | Capability |
|---|---|
| Player | Move, Attack, Cast, HoldWeapon |
| Clone | Move, Attack, Copy |
| Turret | Target, Shoot |
| Orb | Move, Orbit |
| Zone | Tick, ApplyStatus |
| Projectile | Move, Collide |
| PhantomWeapon | Attack |
| Wall | Collide |

그러면:

```text
Clone → Equip Sword
```

를 AI가 만들어도

`Clone.Grip = 0`

혹은

`Clone lacks HoldWeapon`

때문에 reject.

반대로:

```text
Clone → PhantomWeapon → Attack
```

은 통과.

이게 네 기존 `WorldRule Grip`보다 훨씬 체계적이야.

---

# 5. 진짜 어려운 문제는 Balance Validation임

기존 구조에서는 예를 들어

```text
Damage
cost = 30

Projectile
cost = 35

Repeat
cost = 30

Crit condition
cost = -10
```

해서 총합 85 같은 방식이 가능했잖아.

Rule Graph가 되면 단순 합산은 깨진다.

예를 들어:

> Kill → Explosion

Damage 자체는 30이라고 하자.

그런데 적 20마리가 몰려있으면

```text
Kill
 ↓
Explosion
 ↓
Kill
 ↓
Explosion
 ↓
...
```

이 된다.

단순 Cost는 30인데 실제 가치는 엄청날 수 있음.

따라서 이제 **노드 비용**이 아니라 **Graph의 기대 효과량**을 평가해야 한다고 봐.

---

# 6. 여기서 “Power Model”을 따로 만들자

모든 Rule을 몇 개의 공통적인 게임 가치로 환산한다.

예를 들어:

```text
PowerVector {
    DPS
    Burst
    Defense
    Sustain
    Mobility
    Control
    Economy
    Scaling
    Reliability
}
```

어떤 능력이

> Perfect Dodge → 100 Damage Nova

라면

```text
Damage = 100
Expected Perfect Dodge frequency = 0.15/sec

Expected DPS ≈ 15
```

정도로 계산할 수 있다.

반면

> Attack → 20 Damage

라면

```text
Attack frequency = 1.5/sec

Expected DPS ≈ 30
```

이런 식.

즉 Trigger의 발생 빈도가 **효과의 가격을 할인/증폭**한다.

---

# 7. Condition도 이제 그냥 `cost -10`이 아니게 됨

예를 들어:

```text
Damage 100
```

와

```text
IF Health < 20%
    Damage 100
```

은 다르잖아.

그래서 조건에는 `Availability`를 추정한다.

예:

```text
HealthBelow(20%)
Availability ≈ 0.15

TargetPoisoned
Availability ≈ 0.40

EveryThirdAttack
Availability ≈ 0.33

PerfectDodge
Frequency ≈ player-dependent
```

그러면 대략

`ExpectedPower = EffectPower × TriggerFrequency × ConditionAvailability`

같은 기본 모델을 만들 수 있음.

물론 실제 계산은 이것보다 복잡해지겠지만 기본 철학은 이거야.

---

# 8. 그런데 Rule-to-Rule 능력은 어떻게 검증하냐?

여기가 진짜 재미있는 문제야.

예를 들어:

> 모든 Fire 능력이 한 번 더 발동한다.

이 능력의 power는 고정되어 있지 않아.

Fire 능력이 하나면 약하고 7개면 미친 능력이 됨.

그래서 이런 능력은 **Context-dependent evaluation**을 해야 해.

현재 플레이어 빌드를 `B`라고 하면:

```text
Power(Ability, B)
```

를 계산하는 거야.

예를 들어 현재:

```text
Fireball     25 DPS
FireNova     12 DPS
Burn         18 DPS

Total Fire contribution = 55 DPS
```

이라면

```text
Repeat(All Fire Effects)
```

의 이론적 추가 power는 대략

`+55 DPS`

로 평가할 수 있겠지.

---

# 9. 오히려 이게 우리 게임 컨셉하고 잘 맞는다

우리 게임에서는 원래 AI가 **플레이어의 현재 빌드와 행동을 보고 능력을 생성**하려 했잖아.

그렇다면 능력의 밸런스도 절대적인 숫자로만 평가할 필요가 없어.

```text
Player State
      ↓
Candidate Ability 생성
      ↓
Candidate를 현재 Build에 가상 적용
      ↓
Before / After Power 비교
```

하면 된다.

예를 들어:

```text
Current Build Power
= 427

Candidate 적용
= 493

ΔPower = +66
```

현재 진화 단계의 허용 budget이

```text
Target ΔPower = 50~70
```

이라면 ACCEPT.

반대로

```text
Current = 427
After = 891

Δ = +464
```

면 REJECT 또는 숫자 nerf.

이 방식이 꽤 중요할 것 같아.

---

# 10. 그리고 수치 계산으로 안 잡히는 건 Simulation으로 잡자

여기서 나는 **Static Validator + Simulation Validator** 조합을 추천해.

Static analysis가 먼저 빠르게 검사하고:

```text
Infinite recursion?
Invalid reference?
Impossible target?
Spawn explosion?
Illegal state mutation?
Power estimate too high?
```

통과하면 짧은 headless simulation을 돌리는 거야.

예를 들어 내부적으로:

```text
Candidate Ability

→ 100 combat simulations

Normal mobs
Elite
Boss
Dense swarm
Projectile-heavy enemies
Low HP situation
High HP situation
```

그리고

```text
DPS +18%
Survival +11%
Mobility +3%
Average entities: 4.2
Peak entities: 11
Proc/sec: 7.3
CPU budget: OK
```

를 얻는다.

이건 Unity에서도 충분히 현실적으로 구현 가능해.

**그래픽/물리 전체를 실제로 렌더링할 필요가 없다.**

간단한 combat simulator를 따로 만들면 된다.

---

# 11. 그래도 시뮬레이션으로 못 잡는 괴물들이 있음

예:

> Dash 거리가 길수록 다음 공격 피해 증가.

이건 괜찮다.

그런데

> Dash할 때마다 Dash cooldown 20% 감소.

그리고 다른 능력:

> Skill 사용 시 Dash cooldown 감소.

그리고:

> Dash 시 Skill cooldown 감소.

이런 것들이 만나면 **feedback loop**가 생긴다.

그래서 Rule Graph 자체를 분석해야 함.

```text
Dash
 ↓
DashCooldown ↓
 ↓
More Dash
 ↓
DashCooldown ↓
```

이런 **positive feedback cycle**을 검출한다.

Cycle 자체를 금지할 필요는 없어.

오히려 로그라이크에서 재밌으니까.

대신:

```text
Cycle Gain < threshold
```

를 요구하거나

```text
InternalCooldown
ProcLimit
DiminishingReturn
ResourceCost
```

중 하나를 강제로 붙이면 된다.

# 13. Meta Rule에는 더 강한 제한을 걸자

아까 내가 말했던

> 모든 Fire Rule의 Chance를 제거한다.

같은 건 표현력은 미쳤지만 위험하다.

그래서 Rule을 등급으로 나누는 방법도 괜찮아.

### Tier 0 — Value

```text
Damage +20
AttackSpeed +10%
```

매우 안전.

### Tier 1 — Effect

```text
Hit → Burn
Dash → Projectile
```

현재 시스템.

### Tier 2 — Stateful Rule

```text
Kill → Stack += 1

Stack >= 5
→ Damage +50%
→ Stack = 0
```

조금 복잡.

### Tier 3 — Rule Modifier

```text
Fire effects Repeat
Dash effects inherit Lightning
```

강력.

### Tier 4 — System Modifier

```text
Ability selection +1
Rarity modification
Enemy evolution modification
```

매우 강력.

그리고 진화 단계에 따라서 허용할 수도 있다.

초반:

```text
Tier ≤ 1
```

중반:

```text
Tier ≤ 2
```

후반:

```text
Tier ≤ 3
```

특수/전설급:

```text
Tier 4
```

이러면 **괴상한 능력 자체가 rarity가 된다.**

이거 꽤 괜찮다고 봐.

# 14. 그런데 여기서 아주 중요한 설계 원칙 하나

**LLM에게 완성된 Rule Graph를 처음부터 마음대로 쓰게 하지 않는 방법**도 고려해야 해.

나는 오히려:

```text
LLM
 ↓
Ability Intent
 ↓
Compiler
 ↓
Rule Graph
```

를 추천해.

예를 들어 LLM:

```text
Intent:
"Reward repeated perfect dodges with a powerful
clone-assisted counterattack."

Mechanics:
- accumulate perfect dodges
- after threshold empower next melee attack
- clone copies empowered attack
- consume stacks
```

그다음 우리가 만든 **Ability Compiler**가:

```text
Counter
Threshold
ModifyNext
Copy
Consume
```

를 찾아서 실제 Rule Graph를 만든다.

왜냐하면 LLM에게 AST/Graph를 직접 쓰게 하면 syntax 오류나 이상한 연결이 계속 생길 수 있기 때문이야.

AI는 **창의적인 부분**을 담당하고,

Compiler는 **기계적인 부분**을 담당하는 거지.

# 16. 그리고 여기서 자유도를 일부러 제한해야 한다

이게 가장 중요한 결론일 수도 있어.

우리가 원하는 건

> AI가 무엇이든 만들 수 있다.

가 아니야.

그건 구현 불가능하고 검증도 불가능하다.

우리가 원하는 건:

> **개발자가 일일이 상상하지 않은 능력이 나올 만큼 충분히 넓지만, 모든 결과를 기계적으로 실행하고 검증할 수 있을 만큼 닫혀 있는 공간.**

이거야.

수학적으로 비유하면 우리가 **가능한 능력들의 생성자(generator)**를 만들고 있는 셈이야.

개발자는

`Damage`, `Counter`, `Transform`, `Select`, `Modify`, `Repeat`, `State`, `Scale`, `Convert`...

같은 생성자와 합성 규칙만 정의한다.

AI는 그 생성자들을 우리가 예상하지 못한 방식으로 합성한다.

그래서 **“개발자가 생각하지 못한 능력”이 나오는 것과 “개발자가 구현하지 않은 동작”이 나오는 것은 완전히 다르다.**

우리가 원하는 건 전자야.

---

## 그래서 나는 구조를 이렇게 타협하는 게 제일 좋아 보여

**Primitive는 폐쇄적(closed)**이어야 한다. Runtime에서 가능한 동작은 100% 개발자가 구현한다.

**Composition은 개방적(open)**이어야 한다. AI가 Primitive를 어떻게 연결할지는 최대한 자유롭게 둔다.

**Meta modification은 제한적(restricted)**이어야 한다. Rule→Rule 조작은 허용하되 whitelist와 tier/budget을 둔다.

**Validation은 deterministic**이어야 한다. LLM이 “이거 밸런스 괜찮음”이라고 판단하는 건 참고조차 하지 않고 Type/Safety/Power/Simulation으로 검사한다.

이 네 원칙이면 **TFT 증강이나 세피리아 아티팩트 정도의 다양성을 향해 가면서도 실제 Unity 게임으로 구현 가능한 범위**를 유지할 수 있다고 봐.

그리고 다음 설계에서 제일 먼저 할 일은 Primitive를 더 만드는 게 아니라 **`Rule IR`의 실제 데이터 구조를 설계하는 것** 같아. `Rule`, `State`, `Selector`, `Modifier`, `Operator`, `Reference` 정도의 최소 타입만 가지고 실제 TFT/세피리아식 능력 10~20개를 표현해보면, 이 아이디어가 진짜 작동하는지 바로 드러날 거야. memcite

===== user =====
자 그러면 지금까지 우리가 말한 것을 토대로 구조를 구체화하고, 그 구조에 들어갈 db 풀도 구체적으로 생성해줘 줘봐. 나는 이 대화를 클로드에게 공유해서 실제 구현하라고 할 예정이기 때문이야

===== assistant =====

그리고 Claude에게 넘길 구현 명세라 생각하고 구체적으로 적어볼게. 핵심 목표는 다음 한 문장이다.

> **LLM은 개발자가 미리 만든 기술을 고르는 것이 아니라 새로운 Rule Graph를 창작한다. 단, Graph를 구성하는 원자 연산은 엔진에 구현된 것만 사용할 수 있으며, 생성 결과는 타입·실행 가능성·안전성·밸런스를 deterministic하게 검증할 수 있어야 한다.**

기존에 잡아둔 `Gameplay → Feature Extraction → Player Profile → AI Context → AI Concept → Interpreter → Validation → Skill` 흐름도 그대로 살린다. memcite

# 1. 이제 Ability의 정의부터 바꾸자

기존:

```text
Ability
= Event + Condition + Action + Relation + Entity + ...
```

새 구조:

```text
Ability
= State Variables
+ Rule[]
+ Metadata
```

즉 하나의 Ability가 **여러 Rule로 이루어진 작은 프로그램**이다.

예를 들어:

> 완벽 회피 3회마다 다음 근접 공격을 분신이 복제한다.

는

```text
Ability
│
├─ State
│   └─ dodgeStacks : Integer [0..3]
│
├─ Rule A
│   PerfectDodge
│       → Add(dodgeStacks, 1)
│
└─ Rule B
    MeleeAttack
       IF dodgeStacks >= 3
       → CopyAttack(Clone)
       → Set(dodgeStacks, 0)
```

가 된다.

# 2. 최상위 데이터 구조

C# 관점에서 대략 이렇게 시작하는 걸 추천한다.

```csharp
public class AbilityDefinition
{
    public string Id;
    public string Name;

    public List<StateDefinition> States;
    public List<RuleDefinition> Rules;

    public AbilityMetadata Metadata;
}
```

Rule은:

```csharp
public class RuleDefinition
{
    public string Id;

    public TriggerNode Trigger;

    public List<ConditionNode> Conditions;
    public List<OperationNode> Operations;

    public RuleLimits Limits;
}
```

다만 이후 복잡한 Rule-to-Rule 구조를 위해 내부적으로는:

```text
RuleGraph
    Nodes[]
    Edges[]
```

형태로 확장 가능하게 만들어두는 게 좋다.

# 6. State DB

여기서 기존 DSL과 확 차이가 난다.

능력이 자기 상태를 가질 수 있다.

지원할 State 타입:

| State | 용도 |
|---|---|
| Counter | 횟수 |
| Stack | 중첩 |
| Charge | 충전 |
| Timer | 시간 |
| StoredValue | 피해량 등 저장 |
| Flag | true/false |
| Reference | Target/Entity 기억 |
| Position | 위치 기억 |
| History | 최근 N개 사건 |
| TagMemory | 최근 사용 Element 등 |

예:

```text
Counter
name = PerfectDodgeStack
min = 0
max = 5
initial = 0
```

또는

```text
StoredValue
name = StoredDamage
min = 0
```

## Claude에게 우선 구현시킬 범위

한 번에 위의 모든 DB를 구현시키기보다는 **첫 구현에서는 아키텍처를 완성하고 primitive 수만 제한**하는 게 좋다.

1차 구현은 `State(Counter/StoredValue/Flag)`, `Trigger 15~20개`, `Selector 10개`, `Condition 10개`, `Operation 15~20개`, `Relation 5~10개`, `Meta Operation 2~3개` 정도면 충분하다. 대신 **Registry/타입 시스템/Rule IR/Validator/Runtime Executor가 이후 primitive 추가만으로 확장되게 만드는 것**을 최우선으로 해야 한다.

그 다음 현재 AbilityLanguage의 기존 원소들을 새 Registry로 옮기고, 위에서 만든 **잔영 반격 / 역병 / 고통의 기억 / 원소 집착 / 메아리치는 불꽃** 같은 서로 구조가 다른 테스트 능력을 전부 손으로 Rule IR로 작성해서 실행시켜 보면 된다. 이 5종이 같은 Runtime에서 특별 취급 없이 돌아간다면 아키텍처의 1차 성공으로 볼 수 있어.

그 상태부터 DB 풀을 대규모로 채우고 LLM 생성기를 연결하는 게 순서상 맞다. **LLM 연결은 오히려 마지막이다.** 먼저 사람이 Rule IR을 작성했을 때 다양한 능력이 표현되고, validator가 이상한 능력을 확실하게 거절하는지가 증명되어야 한다.
